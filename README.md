# Q-documents

製造現場の品質文書（PFMEA / QC工程表 / 作業指示書）を管理するWebアプリケーション。
文書番号の採番、台帳管理、改訂、旧版の自動アーカイブをブラウザ上で完結させる。

> **開発中（2026/7/31 〜 8/24）。** 本READMEは暫定版です。完成時に設計の要約と実運用時の課題を追記します。

## 背景

品質文書の台帳をエクセルで手作業管理しているため、記入漏れ・採番ルール違反・旧版の誤使用が発生している。
新規文書発行にかかる時間を30分から10分以下にすることを目標とする。

## 実運用時の課題

開発の過程で把握している制約を、判断の理由とともに記録する。完成時にさらに追記する。

### 合言葉の変更は、他の端末へ即座には伝わらない

合言葉を変更すると、トークンの署名鍵も同時に更新して既存の解除をすべて無効にする。
ただし反映のされ方に2つの遅れがある。

**① 他の端末の画面は「解除中」の表示のまま残る。** 画面の解除状態はブラウザ側が保持しており、
サーバーから通知する仕組みが無いため、次にサーバーへ問い合わせるまで表示が変わらない。
**ただしその状態で行える操作は無く**、エクセルの取得も書き込みもすべて401で拒否され、
その時点で解除画面へ戻る。表示を即座に揃えるには画面側の定期確認が要るが、
確認専用のエンドポイントが無く一覧取得が全件スキャンであること、Lambdaの同時実行上限が10であることから、
この規模では採らなかった。

**② 発行済みトークンは最大5分間そのまま通る。** 合言葉と署名鍵は SSM Parameter Store から
読み出し、Lambda の実行環境ごとに5分間キャッシュしている（リクエストのたびに読むと
SSMのレート上限に先に当たるため）。

**解除（合言葉の照合）は、この制限を受けない。** 利用者が1日に数回行うだけの操作なので、
そのつどキャッシュを迂回して読み直している。古い合言葉での解除は変更後ただちに通らなくなる
（誤った合言葉が短時間に何度も続いた直後だけは、連打対策の上限に当たって一時的にキャッシュを使う）。

残るのは**トークンの検証**で、こちらは全リクエストが通る経路のためキャッシュを外せない。
そのため、変更前に発行されたトークンが最大5分間そのまま通用する。署名が合わなかったときは
読み直して確かめ直すので、**新しいトークンが古い鍵で拒否される側は起きない**（読み直しには
連打対策の上限があり、短時間に誤った入力が続いた直後だけは例外的に起こりうる）。一方で
**古いトークンがまだ通る側は残る**（署名の照合に成功してしまい、読み直しの引き金が引かれない）。

**この遅れは受け入れている。** 社内ネットワークの内側でのみ使うアプリで、合言葉は
「生産技術以外に台帳の中身を触らせない」ための区切りである。変更の頻度も低く、
周知のうえで行う運用を前提とするため、数分の反映待ちが業務上の問題にならない。
即時性を求めると、画面側の定期確認やリクエストごとの SSM 読み出しが必要になり、
コストと複雑さが釣り合わない。

### 合言葉が分からなくなったときの復旧

画面から合言葉を変更できるが、**打ち間違いや意図しない変更で誰も解除できなくなった場合、
戻す手段は画面の中に無い**（変更するにも合言葉が要るため）。

**リセットはアプリの外に置いている。** 合言葉を要求すれば締め出された状況では使えず、
要求しなければ社内IPの内側にいる誰でも合言葉を変えられてしまい、合言葉で区切っている
意味がなくなる。復旧の権限は AWS アカウントを持つ人だけが持つべきもので、
そこが正しい置き場所になる。

```bash
./scripts/reset-passphrase.sh
```

書き込み先のアカウント・リージョン・対象パラメータを表示して確認を取り、新しい合言葉を
伏字で2回入力させる。署名鍵も同時に更新するか（＝解除中の端末をすべて終了させるか）は
実行時に選ぶ。**値は Terraform にも state にも渡らない。**

反映には上記のとおり最大5分かかる。**待つのが通常の手順**で、それまでは古い合言葉でも
解除できることがある。

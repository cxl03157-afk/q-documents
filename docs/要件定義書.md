# 要件書　品質文書管理アプリ「Q-documents」

## 1. 背景・目的

### 背景

組み立て工場では既存製品の組み立て手順変更や、新規製品の組み立て手順のためPFMEA、QC工程表、作業手順書を整備する必要がある。 

これらのドキュメントは種類ごとに別々のフォルダで管理される。

またドキュメントにはそれぞれ文書番号が付与され、種類ごとに別々エクセルファイルにて台帳管理される。

台帳更新は手作業であり、複数人が使用するため以下の課題がある。

- 台帳への記入漏れの発生したことがある
- 文書番号が規定通りに付与されなかったことがある
- 改訂版を発行する時に旧版の取り扱いが明確でなく、間違って旧版のドキュメントが使用されることがある
- 作業手順書は工程ごとに作成するが、工程数が20程度あり文書番号が多くなり台帳管理が煩雑である
- 特に人が入れ替わった時に文書番号を把握するのに時間がかかる
- ドキュメントの改定時、関連するドキュメントの変更も必要となる場合があるが、調べるのに時間がかかることがある
- 製造中止などで材料などが変更になるときにどの文書を改定すれば良いか特定するのに時間がかかる
- 文書の承認回覧はメールにより依頼であり、担当者以外は進捗状況が分からない
- 文書が別々のフォルダに保管されており、必要な時に文書を探しにくい
- ドキュメント管理用のソフトウエアは世の中に存在するが予算の認可が降りず、現状方法を踏襲し続けている

※文書は2種類あり、エクセルが原本、これをPDFにして製造に配布する。これらの文書は社外に出せない会社の秘密情報であり、社内関係者のみが扱う

### 目的

台帳への記入漏れを防止し、文書番号が規定通りに付与されるようにする。

旧版のドキュメントが使用されないようにする。

文書の検索や回覧、管理の手間を小さくする。

新規文書の場合：付与する文書番号のルール確認、採番、台帳への記入など　30分　→　10分以下

## 3. 解決方針

- PFMEA、QC工程表、作業指示書がアップロードされたら、文書番号を自動的に抜き出して台帳に存在するか確認する（アップロードするときのファイル名は文書番号を含む）
- ドキュメントの文書番号を入力情報から自動生成する（新規作成の場合）。
- リビジョン番号も現行文書を選んでボタンひとつで更新する（文書更新の場合）。
- 文書の改訂と同時に旧版の文書をアーカイブし、通常は最新版の文書のみを表示させる（生産技術は合言葉により旧版も参照できる）
- 台帳管理の煩雑さはフィルタリング機能で表示をわかりやすくする
- 文書種類・キーワード検索と、PFMEA↔QC工程表↔作業指示書の紐付け表示する。
- 材料名などで検索して、関連する文書番号を全て表示させる
- 管理表を複数のエクセルファイルからDB管理にし、必要な時はいつでも一覧表示できるようにする。
- 文書の承認回覧を開始したら自動で次の確認者にメール配信するようにする
- また回覧の状況がわかるダッシュボードを作成する
- 文書は１箇所に集め、検索しやすいようにする
- PC不慣れな人でも扱いやすいように、文字入力を少なくし、選択肢マスタからプルダウンで選択する方法とする。閲覧のみの利用者（現場工程リーダーなど）は氏名選択も不要で、一覧の絞り込みだけで文書に到達できる
- 予算が確保できない前提で、運用負担低減のため、AWSサーバーレス構成とする

※GitHubでも履歴管理はできるが、利用者全員にGitHubの仕組みを理解させることはかなりの労力がかかるため、Webブラウザで完結する専用アプリとする。

**「主要ユースケース」** 

- 新規文書発行時：文書管理者（生産技術）が必要情報を入力する（選択肢マスタからプルダウンで選択）　→　選択肢マスタに存在しない製品コード等がある場合は、文書管理者がマスタに追加してから入力　→　命名ルールに従った文書番号が生成される　→　担当者に文書番号を表示する　→　OKすると文書番号が記録される　→　担当者が文書に文書番号を記入する、また文書番号を含めたファイル名を付ける　→　担当者が 文書のアップロード操作をする（PDFとエクセルの２種類）　→　台帳に文書番号がある場合は、OK表示をして文書を保管する、台帳に文書番号がなかった場合は、エラー表示を行い文書の記録はしない
- 既存文書の改訂：担当者が既存の文書番号を選択　→　対象文書名と新旧リビジョンを確認画面に表示　→　OKすると文書番号更新、記録　→ 　担当者が文書に文書番号を記入する、また文書番号を含めたファイル名を付ける　→　　　担当者が 文書のアップロード操作をする（PDFとエクセルの２種類）　→　台帳に文書番号がある場合は、OK表示をして保管後に旧版をアーカイブし、通常の閲覧では表示されないようにする（生産技術は合言葉により参照できる）、台帳に文書番号がなかった場合は、エラー表示を行い文書の記録はしない
- 検索・閲覧：選択マスタからプルダウンで製品コード、工程番号、工程名、文書種類を選択する、必要に応じて複数を選択できる　→　選択された項目に従って台帳をフィルタリングして結果を一覧表示する、必要に応じてCSV形式でダウンロードできる

### 5.1 セキュリティ要件

1. 通信はHTTPSのみとし、HTTP接続は拒否する
2. 保管時の暗号化：S3はSSE-S3、DynamoDBは保管時暗号化を有効にする
3. 画面・APIともに社内ネットワーク(グローバルIP)からのアクセスのみ許可する
4. S3バケットは公開せず、ファイルへのアクセスは署名付きURL経由のみとする
5. 署名付きURLの有効期限は15分以内とする
6. Lambda実行ロールは対象リソースとアクションを限定した最小権限とする
7. ファイル名の形式・拡張子・文書番号の一致をサーバー側で検証し、パストラバーサルおよび不正なファイルの登録を防止する。画面側の検証だけに依存しない
8. 個人情報は氏名のみ扱う
9. ダウンロード後のファイル管理は本アプリの範囲外とし、運用規程で対応する
10. 生産技術用の合言葉をサーバー側で検証する。対象は①エクセル・旧版ファイルの署名付きURL発行、②台帳・マスタへの書き込み操作（登録・修正・削除・リビジョンアップ・アップロード）の2種
11. 合言葉は SSM Parameter Store（SecureString）で管理し、コードやTerraform stateに平文で残さない
12. エクセル・旧版へのアクセス時は、選択された氏名・対象文書・日時をCloudWatch Logsに記録する

## 7. 完成の定義(受け入れ基準)

- 新規文書作成時に必要情報を入力すると、命名ルールに従った文書番号が作成されDBに登録される
- 現行文書を選んでボタンを押すとRev1→Rev2のように更新でき、DBに登録される
- 文書をアップロードしたら、その文書の文書番号が台帳に存在することを確認できる
- 文書をアップロードした時に、PDFファイルとエクセルファイルが保管されている
- 改訂文書をアップロードしたら旧版の文書をアーカイブして、最新版のみ表示する
- 台帳を製品コード、工程番号、工程名、文書種類、状態を使ってフィルタリングして表示できる
- 文書を選択するとそれと関連するPFMEA、QC工程表、作業指示書の文書番号が表示できる
- 台帳の一覧をWeb上で表示できる
- 台帳の一覧、フィルタリングした台帳の内容をCSV形式でダウンロードできる
- 操作時に選択肢マスタでプルダウン選択でき、合言葉を入力した文書管理者（生産技術）はマスタの内容を編集できる
- 上記がAWS上でサーバーレスで動作し、月間コストが1,000円以内である
- 登録済み・旧版・未登録番号の文書をアップロードすると、それぞれ理由が表示され登録されないこと
- PDFを2つ選ぶなど、欄とファイル種別が一致しない場合は理由が表示され登録されないこと
- 画面側の検証を回避してAPIを直接呼んでも、不正なファイル名では署名付きURLが発行されないこと
- 一覧の各行から該当する文書ファイルを開く・ダウンロードできる
- 文書管理者（生産技術）が誤登録レコードを修正・論理削除でき、論理削除したレコードは一覧に表示されない
- PDF・Excelの2種別を登録でき、それぞれ閲覧・ダウンロードできる
- 合言葉を入力していない状態では、最新版のPDFのみが表示・ダウンロードできる
- 氏名を選択し合言葉を入力すると、エクセルおよび旧版が表示・ダウンロードできる
- 画面側の制御を回避してAPIを直接呼んでも、合言葉なしではエクセルの署名付きURLが発行されない
- 合言葉なしでは台帳レコードの登録・修正・論理削除、マスタの編集ができない
- エクセル・旧版をダウンロードすると、氏名・文書番号・日時がログに記録される
- HTTPでアクセスするとHTTPSにリダイレクトまたは拒否される
- 社外のIPアドレスからは画面・APIともにアクセスできない
- S3バケットのURLを直接叩いてもファイルが取得できない

# Claude Code 起動プロンプト集

Claude Code でセッションを開始するときに貼り付ける固定プロンプト集。

**運用モデル**: Claude Code 単独。外部エージェント（Codex / Composer）は使用しない。

`CLAUDE.md` はセッション開始時に自動で読み込まれるため、貼り付ける必要はない。

---

## 0) セッション開始（標準）

```text
Q-documents の作業を続けてください。

最初に以下の1ファイルだけ読み、3行で現状を要約してください。
- docs/context.md

詳細確認が必要な場合のみ以下を参照してください。
- docs/phase-roadmap.md（当日の作業内容）
- 対象 Issue

次に、次の1アクションだけ提案してください。
承認したら実行してください。

制約:
- 実装に入る前に、何をどう書くかを日本語で説明し、承認を得ること
- ユーザーの明示承認なしに gh pr merge は実行しない
```

---

## 1) 計画フェーズ起動

```text
Q-documents の作業を続けてください。

docs/context.md と docs/phase-roadmap.md を読んで現状を把握後、以下を実施してください。
1. 当日の目的・完了条件・リスクを提示
2. 実装順序を 3〜7 ステップで提案
3. docs/context.md の NextAction / 決定事項 に反映すべき差分を列挙

制約:
- 実装は行わない
- 計画の矛盾・漏れを優先して指摘する
- 承認後に実装フェーズへ移行する
- ユーザーの明示承認なしに gh pr merge は実行しない
```

---

## 2) 実装フェーズ起動

```text
Q-documents の作業を続けてください。

docs/context.md を読んで現状を把握後、NextAction のみを実行対象にしてください。

実行ルール:
- **コードを書く前に、何をどう書くかを日本語で説明し、承認を得る**
  （ファイル構成・関数の責務・データの流れ・エラー時の挙動）
- 複数の副作用にまたがる処理は、異常系の設計も説明に含める
- 実行前に CLAUDE.md の該当ルールだけ確認する
- スコープを勝手に広げない
- コミット前に diff とメッセージ案を提示し承認を得る
- 実装後にテスト/検証結果を提示する（lint → test → build の順）
- PR 作成前に連絡する
- ユーザーの明示承認なしに gh pr merge は実行しない
```

---

## 3) セルフレビュー

```text
Q-documents の作業を続けてください。

docs/context.md を読んで現状を把握後、最新差分をレビューしてください。

レビュー観点:
1. 仕様整合（要件定義書・screens.md・API.md・DynamoDBテーブル設計.md）
2. CLAUDE.md §8 セキュリティの不変条件に反していないか
   （合言葉の平文・社内IPのコミット・サーバー側検証の省略・署名付きURLの条件）
3. 状態遷移の規律（状態を書き換えるのは非同期Lambdaだけか、冪等性は担保されているか）
4. テスト不足

出力形式:
- Findings（重大度順）
- Residual Risks
- Ready for merge?（Yes / No + 理由）

制約:
- ユーザーの明示承認なしに gh pr merge は実行しない
```

---

## 4) CI 修正

```text
Q-documents の作業を続けてください。

docs/context.md を読んで現状を把握後、対象 PR の CI 失敗原因だけを調査してください。

実行ルール:
- まず `gh pr checks <PR番号>` で失敗箇所を確認する
- 失敗している lint / test / build だけを対象にする
- 関係ないリファクタや仕様変更は行わない
- 修正前に原因と修正方針を提示し、承認を得る
- コミット前に diff とメッセージ案を提示し承認を得る
- 修正後に該当コマンドをローカルで再実行する
- ユーザーの明示承認なしに gh pr merge は実行しない

出力:
- 原因
- 修正内容
- 実行した検証コマンド
- 残リスク
```

---

## 5) 受け入れ基準の確認（週3後半〜週4で使う）

```text
Q-documents の受け入れ基準を確認します。

要件定義書.md §7 の25項目のうち、以下を確認対象にしてください。
（対象項目をここに列挙する）

各項目について:
- 実際に操作またはコマンドを実行して確認する（コードを読んだだけで「満たしている」と判断しない）
- 結果を「合格 / 不合格 / 未実施」で報告する
- 不合格の場合は、原因と修正案を提示する（修正はこの場では行わない）

確認結果を docs/context.md の受け入れ基準の消化数に反映してください。
```

## 更新ルール

- 作業の区切りごとに `docs/context.md` を最新化してから次のセッションを開始する
- このファイルのプロンプトを変更したら、`docs/phase-gates.md` の該当チェック項目と整合しているか確認する

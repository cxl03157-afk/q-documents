## 3. PR とマージの運用

### 3つを分けて考える

| 操作 | 頻度 | 目的 |
| --- | --- | --- |
| コミット | 作業の区切りごと | 手元の履歴。粗くてよい |
| **プッシュ** | **毎日、最低1回** | **バックアップ**。PRの準備ができていなくても押す |
| PR・マージ | 検証できる単位ごと（1日1本程度） | 自己レビューの区切り、履歴の記録 |

単独開発でマシンが1台なら、ローカルリポジトリが単一障害点になる。**1日の終わりに必ずプッシュする。**

### PR一覧（約22本）

| 週 | PR |
| --- | --- |
| **週1** | ①リポジトリ初期化 ②モック7画面 ③モックのレビュー反映<br>④Terraform: ストレージ層 ⑤Terraform: 公開層 ⑥Hello World疎通＋デプロイスクリプト |
| **週2** | ⑦shared/types＋文書番号パース ⑧合言葉 ⑨採番 ⑩リビジョンアップ<br>⑪マスタCRUD ⑫一覧のAPI接続 |
| **週3** | ⑬状態遷移の純粋関数 ⑭upload-url ⑮アップロード画面<br>⑯非同期Lambda（状態遷移） ⑰非同期Lambda（ストレージクラス）<br>⑱download-url＋閲覧 ⑲関連文書＋CSV ⑳修正・論理削除 |
| **週4** | ㉑README ㉒受け入れ確認で出た修正 |

**22本は平均であって、ノルマではない。** 難所で2日かかる日もあれば、小さいものを2本出せる日もある。週単位で帳尻が合えばよい。

### マージのたびに main が動く状態を保つ

「途中まで実装した状態」を main に入れない。この規律があると、**どこで壊れたかが常に1つ前のマージまで絞り込める。**

### インフラのPRだけ順序が逆

| 種類 | 順序 |
| --- | --- |
| コード（PR⑦〜⑳） | 自己レビュー → **マージ** → デプロイ |
| **インフラ（PR④⑤）** | ブランチ上で `terraform apply` → **成功を確認** → マージ |

適用してみないと通るか分からないため、apply が通ったコードだけを main に入れる。

### Issue は PR より粗く

Issueは機能のまとまり単位（週あたり4〜6本）で切り、1つのIssueに複数のPRがぶら下がる形を許す。22本すべてにIssueを立てると管理コストだけが増える。

## 4. テストの運用

| 種類 | 頻度 | 内容 |
| --- | --- | --- |
| テストを**書く** | **PR⑦とPR⑬のみ** | 純粋関数（文書番号パース・状態遷移判定） |
| テストを**走らせる** | **全PR（CIで自動）** | Lint → Test → **Build** |
| 手動での動作確認 | 全PR（マージ前） | そのPRで何が動くようになったかを実際に触る |
| APIの目視確認 | PR⑨〜⑳ | curl で実際に叩き、レスポンスを目で見る |
| 受け入れ基準の確認 | 該当するPRごと | 25項目を週1〜3に分散して潰す |

**Build を必ずCIに入れる。** lint と test が通ってもビルドで落ちるケースは実際に起きる（TypeScriptの型エラーはビルドでしか出ない）。

**受け入れ基準を週4に全部残さない。** 週4は初回確認ではなく回帰確認とする。

## 5. デプロイ

マージのたびの自動デプロイは行わない。**デプロイスクリプトを週1で作り、週2〜3の全デプロイをそれ経由で行う。**

週4で初めて自動化すると、本番前日に新しい仕組みを導入することになり、そこでハマると詰む。週1で作れば週2〜3の20回以上のデプロイが全てテストになり、週4には枯れた状態になる。

```bash
# scripts/deploy-frontend.sh
npm --prefix frontend run build
aws s3 sync frontend/dist s3://$BUCKET --delete --dryrun    # まず確認
read -p "上記で実行しますか? [y/N] " yn; [ "$yn" = "y" ] || exit 1
aws s3 sync frontend/dist s3://$BUCKET --delete
aws cloudfront create-invalidation --distribution-id $DIST_ID --paths "/*"
```

```bash
# scripts/deploy-backend.sh
npx esbuild backend/src/handlers/api.ts --bundle --platform=node --outfile=dist/api.js
cd dist && zip -q api.zip api.js
aws lambda update-function-code --function-name q-documents-api --zip-file fileb://api.zip
```

`--dryrun` で確認してから本実行、`--delete` 使用時は `--exclude` を付ける — FitLogの運用ルールをスクリプトに焼き込む。手順書に書くより守られる。

## 8. 完了の判定

`要件定義書.md` §7 の受け入れ基準25項目を手動で全件確認する。自動E2Eは期間的に作らない。

特に確認を要するもの:

- 新規発行 → 番号生成 → PDF・エクセル同時アップロード → 「最新」に遷移
- 改訂 → 前リビジョンが「旧版」になり Glacier IR へ移動
- 未登録番号 / 旧版 / 同一種別の重複 の3ケースで理由が表示され登録されない
- 同一リビジョンでも別種別なら登録できる
- **PDFを2つ選ぶと拒否される**
- 合言葉なしで最新PDFのみ、解除でエクセル・旧版が見える
- **画面の制御を回避してAPIを直接叩いても、合言葉なしでは弾かれる**
- HTTP拒否 / 社外IPから到達不可 / S3直叩き不可
- AWS Budgets で月額1,000円以内

# DynamoDBテーブル設計

## 属性

- 文書番号の採番ルール

PFMEA：文書種類_製品コード_リビジョン番号（2桁）

例：文書種類がQ001、製品コードがP-0001、リビジョンが01　→　Q001_P-0001_01

QC工程表：文書種類_製品コード_リビジョン番号（2桁）

例：文書種類がQ005、製品コードがP-0001、リビジョンが01　→　Q005_P-0001_01

作業指示書：製品コード_工程番号_工程名_リビジョン番号（2桁）

例：製品コードがP-0001、工程番号がK001、工程名が工程１、リビジョンが02　→　P-0001_K001_工程1_02

- ファイル名のルール

ファイル名は「文書番号 + 拡張子」とする

例：Q001_P-0001_01.pdf ／ Q001_P-0001_01.xlsx

許容する拡張子：.pdf、.xlsx（大文字小文字は区別しない）

拡張子でファイル種別を判定し、.pdf は S3キー(PDF)、.xlsx は S3キー(Excel) に記録する

- 文書番号について

ステップ1：属性

文書番号、文書種類、工程番号、工程名、リビジョン番号、担当者、登録日、状態（ファイル未登録 / 一部登録 /最新 / 旧版 / 削除済み ）、S3キー（PDF）、S3キー（Excel）

ステップ2：アクセスパターンとの突き合わせ

照合(文書番号で1件引く)

採番(同じ種類・文書IDの現行Revを知る)

関連導出(製品コードで全件引く)

一覧(全件取得)

全ての文書に製品コードが入っているので、これをプライマリーキーにする

リビジョン番号は文書改定毎に変わっていくのでソートキーにこれを含める必要がある

このため文書番号のID部分とリビジョン番号の組み合わせをソートキーにする

例1：文書IDがQ001_P-0001、リビジョンが01の場合、Q001_P-0001#01

例2：文書IDがP-0001_K001_工程1、リビジョンが02の場合、P-0001_K001_工程1#02

ステップ3：キーの決定

文書番号テーブル：PK　製品コード、SK　文書ID#リビジョン  / 属性：文書番号、文書種類、リビジョン番号、担当者、DBへの登録日、文書発行日、状態（ファイル未登録 / 一部登録 /最新 / 旧版 / 削除済み ）、S3キー（PDF）、S3キー（Excel）

- 選択肢マスタについて

ステップ1：属性

文書種類、製品コード、工程番号（工程名）、担当者、状態（有効、無効（削除済み） ）

ステップ2：アクセスパターンとの突き合わせ

プルダウンで選ぶのでそれぞれの項目には関連性はない

項目の種別をプライマリーキーにする

ソートキーには項目の種別に対するコード番号とする

ステップ3：キーの決定

マスタテーブル：PK　項目種別、SK　コード番号  / 属性：工程名、文書種類、氏名、DBへの登録日、状態（ 有効 / 無効（削除済み））

- 担当者マスタについて
登録するのは生産技術の担当者のみとする（文書の担当者になりうる人）。
現場工程リーダー・品質管理者・製品開発者・技術サポーターは登録しない。
表示制御は合言葉で行うため（F-18）、役割を示す属性は持たない。

- 一部登録について
通常フローでは発生しない例外状態、ファイル保存時にエラーが発生し、片方のみ保存された場合に起こる。

## 補足：ファイルアップロード後の非同期処理

実ファイルは署名付きURL（presigned POST）でS3へ直接送る（API Gatewayは経由しない）。

`content-length-range` でサイズ上限を強制するため PUT ではなく POST を使う（CLAUDE.md §8-4）。

送信完了をS3イベント（`s3:ObjectCreated:Post`）で検知し、非同期Lambdaが以下を実行する。

クライアントから呼び出すエンドポイントは持たない。

1. ファイル名から文書番号と拡張子を解析し、S3キー(PDF)またはS3キー(Excel)を台帳に記録する
2. PDF・Excelの両方が揃った場合、状態を「最新」に更新する
  （同時アップロード時の二重実行を防ぐため、条件付き書き込みで先勝ちとする）
3. 同一文書IDの前リビジョンを「旧版」に更新し、両ファイルをGlacier IRへ移行する

対応機能：F-04（自動アーカイブ）、F-07（台帳への保管）

## 補足：合言葉による制御について

**合言葉トークンを要求する範囲**


| 対象                                       | 要否    | 理由                                     |
| ---------------------------------------- | ----- | -------------------------------------- |
| 書き込み系すべて（登録・修正・削除・リビジョンアップ・マスタ編集・アップロード） | **要** | いずれも生産技術だけが行う操作。合言葉がないと誰でも台帳を削除・改ざんできる |
| エクセル・旧版のファイル取得                           | **要** | エクセルは原本であり、旧版は誤使用の原因になる                |
| 最新版PDFのファイル取得                            | 不要    | 全利用者が閲覧してよい                            |
| 読み取り専用のGET（一覧・マスタ取得・番号プレビュー）             | 不要    | 台帳のメタデータは社内利用者に隠す必要がない                 |


**検証はサーバー側で行う。** 画面側だけの制御では開発者ツールから回避できるため、
Lambda が SSM Parameter Store から読み出した合言葉と照合してからトークンを発行し、
以降のリクエストではトークンを検証する。

**一覧の「表示」は画面側で行う。**
`GET /documents` は旧版を含む全件を返す。**論理削除は既定で除外**するが、
合言葉トークンを添えた場合のみ削除済みも含めて返す（文書管理者が何を消したかを追えるようにするため）。
削除済みのファイル取得はエクセルに限る（PDFは配布物のため、消した版を現場に出さない）。

どの行をどう見せるかは画面側が判断する。

**合言葉は個人を認証するものではない。**
役割単位（生産技術）で共有する1つの値であり、氏名は自己申告である。
記録は本人性の証明ではなく抑止力として機能する（要件定義書 §4.3）。

**トークンの仕様**


| 項目         | 内容                                                                                                                                                |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| 形式         | `base64url(ペイロード).base64url(HMAC-SHA256)` の2部構成。JWT は使わない                                                                                         |
| 署名鍵        | 合言葉とは別の SSM パラメータ（`/q-documents/token-secret`・SecureString）。分けているのは、①人が覚える合言葉を鍵に使うと、トークンを1つ入手した相手が手元の総当たりで合言葉を復元できるため ②鍵だけを単独で更新して全員を締め出せるようにするため |
| サーバー側の有効期限 | **2時間**。画面側の「30分の無操作で自動ロック」とは目的が違う（画面＝離席対策 / サーバー＝盗まれたトークンが使われ続けないための上限）                                                                          |
| 送り方        | `Authorization: Bearer <token>`                                                                                                                   |


`POST /auth/unlock` の成功応答は次の3つを返す。

```
{ "token": "...", "expiresAt": "2026-08-09T12:00:00.000Z", "expiresInSeconds": 7200 }
```

**画面側は** `expiresInSeconds` **を使う。** `expiresAt` はサーバーが生成した絶対時刻なので、
画面が自分の時計と引き算すると2つの時計をまたぐことになり、端末の時計がずれていると
「解除しても解除されない」状態になる。`expiresAt` は表示・ログ突き合わせ用に残す。

**合言葉を変更すると、発行済みのトークンもすべて失効する**（署名鍵を同時に更新するため）。
詳細は「補足：合言葉の変更（F-20）」を参照。

## 補足：upload-url のファイル名検証

`POST /documents/{docNo}/upload-url` は **1つまたは2つ**のファイル名を受け取り、
**署名付きURLを発行する前に**以下を検証する。1つでも満たさなければURLを発行しない。

既に登録済みの種別は再登録できないが、未登録の種別だけを後から追加できる（F-01）。
検証1〜5は送られてきたものについてだけ行い、検証3は2つ送られてきたときだけ行う。

1. PDF側のファイル名が `.pdf` で終わること
2. エクセル側のファイル名が `.xlsx` で終わること
3. 2つのファイル名の文書番号部分が一致すること
4. 文書番号がパスの `{docNo}` と一致すること
5. 文書番号が命名ルールの形式に従うこと（`../` や `/` を含まないこと）
6. 台帳照合（F-01）：未登録番号・旧版リビジョン・削除済み のいずれでもないこと
7. **要求された種別が未登録であること。** 判断は状態ではなく台帳のS3キーの有無で行う

画面側でも同じ検証を行うが、**サーバー側の検証を正とする**。
画面側だけの検証では、開発者ツールから直接APIを呼ばれた場合に壊れたデータが登録されてしまう。

具体的には、エクセル欄にPDFを選んだまま通過すると、S3の `.xlsx` キーにPDFの実体が保存され、
非同期Lambdaは「両方揃った」と判断して状態を「最新」にする。
台帳上は正常に見えるため、後日エクセルを開くまで誤りに気づけない。

発行する署名付きURLには `Content-Type` を署名条件に含める。
エクセル用URLに `Content-Type: application/pdf` を宣言して送ると、S3側で 403 になる（実測済み）。

**ただしこれは「宣言した種別」に対する防御であって、中身の検査ではない。**
拡張子を `.xlsx` に書き換えたPDFは、`Content-Type` がエクセルとして送られるため通ってしまう。
中身と拡張子の食い違いを見るのは F-19（ファイル内容の検証・ストレッチ）の担当。

なお**キーはファイル名ではなく文書番号から組み立てる**（`{製品コード}/{文書番号}.{拡張子}`）。
クライアントはキーを選べないので、`.xlsx` キーに実体が入るかどうかは
「エクセル用のURLを使ったかどうか」だけで決まる。

## 補足：セキュリティ

- APIは社内ネットワークのグローバルIPからのみ受け付ける(API Gateway REST APIのリソースポリシー)
- CORSは自サイトのオリジンのみ許可し、ワイルドカードは使用しない
- 署名付きURLの有効期限は15分以内とする
- アップロード用の署名付きURLには content-length-range を含め、ファイルサイズ上限を強制する
- ファイル名の検証は「補足：upload-url のファイル名検証」を参照（パストラバーサル対策を含む）
- 合言葉は SSM Parameter Store（SecureString）から読み込み、コードやTerraform stateに平文で残さない
- 合言葉トークンはブラウザのタブを閉じるまで有効（sessionStorage 保持）とし、サーバー側でも有効期限を設ける
- エクセル・旧版のURL発行時は、氏名・文書番号・ファイル種別・日時をCloudWatch Logsに記録する

対応機能：5.1 セキュリティ要件

## 補足：合言葉の変更（F-20）

`POST /auth/passphrase` は、合言葉と署名鍵を**必ず同時に**更新する。合言葉を変える動機は多くの場合「特定の相手を締め出したい」であり、合言葉だけを変えても発行済みトークンは最長2時間そのまま通用するため、それだけでは目的を達しない。

**現在の合言葉が一致しない場合は 403 を返す（401 ではない）。** 画面側は「トークンを付けたのに 401」を受けると解除を終了する仕様のため、401 にすると打ち間違いだけで作業中の解除が切れる。認証は通っているがこの操作を許さない、という意味で 403 とする。

**無効化された担当者は変更できない（403）。** この経路は新しいトークンを発行するので、再確認しないと `POST /auth/unlock` の担当者チェックを迂回してセッションを更新し続けられる。

### 失敗時の応答

SSM への書き込みは2本あり、原子的に行う手段がない。そこで **「照合 → 署名鍵の生成 → トークンの生成 → 署名鍵を保存 → 合言葉を保存」**の順に行い、書き込みのあとに失敗しうる処理を残さない。結果として、**断定できる失敗（何も変わっていない）を1つに寄せ、曖昧さを最後の1か所だけに閉じ込める**。どこまで進んだかは `stage` で区別する。


| status | stage            | 状態                                     | 画面の案内                    |
| ------ | ---------------- | -------------------------------------- | ------------------------ |
| 400    | —                | 形式不正・要件違反（8〜20文字／前後の空白／表示されない文字／現行と同一） | 理由を表示                    |
| 403    | —                | 現在の合言葉が違う／担当者が無効化されている                 | 理由を表示                    |
| 500    | `none`           | **何も変わっていない**                          | そのまま再試行できる               |
| 500    | `secret-rotated` | 署名鍵は更新され、全員の解除が切れた。合言葉が変わったかは判別できない    | 新しい合言葉で解除し直し、入れなければ元の合言葉 |




### 反映のタイミング

合言葉と署名鍵は SSM Parameter Store から読み出し、Lambda の実行環境ごとに
5分間キャッシュしている（リクエストのたびに読むと SSM のレート上限に当たるため）。

- **解除（`POST /auth/unlock`）はキャッシュを使わず毎回読み直す。** 利用者が1日に
数回行うだけの操作なので、古い合言葉が通り続ける状態を残さない
（誤った合言葉が短時間に何度も続いた直後だけは、連打対策の上限に当たって一時的にキャッシュを使う）
- **トークンの検証はキャッシュを使う**（全リクエストが通る経路のため外せない）。
そのため**変更前に発行されたトークンは最大5分間そのまま通用する**。
署名が合わなかったときは読み直して確かめ直すので、新しいトークンが古い鍵で
拒否される側は起きない（読み直しには連打対策の上限があり、短時間に誤った入力が
続いた直後だけは例外的に起こりうる）

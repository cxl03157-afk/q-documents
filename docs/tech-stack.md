# 技術スタック

本書は Q-documents で採用する技術と、その選定理由を記録する。

要件定義書 §6 の制約条件（AWSサーバーレス構成・Terraform・開発期間4週間・開発者1名）を前提に、**「理解を伴う開発」を最優先の判断軸**として選定した。開発期間が４週間のため、**同時に扱う新しい技術を最小限に抑える**方針をとっている。

> バージョンは選定時点の方針を記録したもの。実際の固定値は各 `package.json` / `.terraform.lock.hcl` を正とする。

---

## 選定の判断軸


| 優先度 | 軸              | 具体的な適用                                       |
| --- | -------------- | -------------------------------------------- |
| 1   | 学習対象を増やしすぎない   | 新規に習得するものは TypeScript のみに絞る。React は次案件へ送る    |
| 2   | 全コードを読める規模に収める | 目安 1,800〜3,000行。超え始めたら機能を削る判断をする             |
| 3   | 要件から導出できること    | 特にセキュリティ・コスト要件が構成選択を決定している                   |
| 4   | 主流であること        | TypeScript・Vite・Terraform など、この案件を超えて残る技術を選ぶ |

## フロントエンド


| 技術                        | バージョン | 選定理由                                                                                                                           |
| ------------------------- | ----- | ------------------------------------------------------------------------------------------------------------------------------ |
| TypeScript                | 5.x   | 主流であり、この案件を超えて残る。台帳レコードの型と状態5値をバックエンドと共有できる                                                                                    |
| Vite                      | 最新安定版 | 開発サーバーとビルドの標準。`npm create vite@latest -- --template vanilla-ts` で構成が生成され、設定ファイルを読んで理解できる                                       |
| **フレームワークなし（vanilla TS）** | —     | **React を採用しない判断。** 画面7枚・状態3種程度の規模ではReactの恩恵が学習コストを下回る。DOM操作を明示的に書くことで `fetch` / `array.filter` / `querySelector` という土台が身につく |
| Vitest                    | 最新安定版 | Vite ネイティブ。バックエンドと同一ツールで設定を1本化できる                                                                                              |
| ルーティング（ハッシュ方式）           | —     | `#/documents/new` 形式。`#` 以降はサーバーに送信されないため、S3は常に `index.html` を返す。History API方式だとリロード時に404となり、CloudFront側での書き換え設定が必要になる。IP制限用のCloudFront Functionに別の役割を持たせずに済む |


**CSSはフレームワークを使わない。** 素のCSSで書く。画面数が少なく、Tailwind等の記法を覚える時間を実装に回すため。

## バックエンド（Lambda）


| 技術                     | バージョン  | 選定理由                                                              |
| ---------------------- | ------ | ----------------------------------------------------------------- |
| Node.js                | 22 LTS | Lambda ランタイム `nodejs22.x`。フロントエンドと同一言語で切り替えコストが下がる                |
| TypeScript             | 5.x    | 状態5値（ファイル未登録 / 一部登録 / 最新 / 旧版 / 削除済み）を Union 型で表現し、タイプミスをビルド時に落とす |
| esbuild                | 最新安定版  | Lambda へのバンドルを1コマンドで完結させる。Webpack等より設定が小さく、学習対象を増やさない             |
| AWS SDK for JavaScript | v3     | DynamoDB操作・S3署名付きURL生成。モジュール単位で読み込めるためバンドルサイズが小さい                 |
| Vitest                 | 最新安定版  | フロントエンドと共通                                                        |




### Lambda 関数の構成（2本）


| 関数    | 起動          | 責務                                                                                     |
| ----- | ----------- | -------------------------------------------------------------------------------------- |
| 同期API | API Gateway | 合言葉の検証とトークン発行・採番・照合・リビジョン更新・台帳記録・署名付きURL発行                                             |
| 非同期   | S3 POSTイベント | ①S3キーを台帳に記録 ②両方揃えば「最新」へ（条件付き書き込みで先勝ち） ③前リビジョンを「旧版」+ Glacier IR へ |




### テストを書く範囲

全体網羅はしない。**最も間違えやすい純粋関数に絞る。**

- 文書番号のパース・生成（3種別の形式 → 製品コード・文書ID・リビジョン）
- 状態遷移の判定（両ファイルが揃ったか、前リビジョンをどう扱うか）

それ以外は要件定義書 §7 の受け入れ基準25項目を手動確認する。

## インフラ（本番）


| 技術                          | 用途              | 選定理由                                                                     |
| --------------------------- | --------------- | ------------------------------------------------------------------------ |
| **API Gateway REST API**    | APIの入口          | **HTTP APIはリソースポリシー非対応。**無料でIP制限を実現するにはREST APIが必要（セキュリティ要件 5.1-③）       |
| AWS Lambda                  | アプリケーション実行      | 実行時間課金。サーバー管理作業が発生しない（§5 運用）                                             |
| Amazon S3                   | 文書保管・画面配信の2バケット | ストレージクラスの使い分けで400GBを月額目標内に収める                                            |
| **Amazon CloudFront + OAC** | 画面配信            | **S3静的ウェブサイトホスティングはHTTPS非対応。**HTTPS必須要件（5.1-①）を満たすために必要。無料枠（月1TB転送）内に収まる |
| **CloudFront Functions**    | 画面のIP制限         | WAFは月約900円でコスト要件を超過するため代替。100万リクエストあたり$0.10で実質無料                         |
| Amazon CloudWatch Logs      | ログ・監視           | 不具合発生時の原因確認（§5 ログ・監視）。エクセル・旧版へのアクセス記録もここに出力する（5.1-⑫）                    |
| **AWS SSM Parameter Store** | 合言葉の保管          | 生産技術用の合言葉を SecureString で保管。コードやTerraform stateに平文で残さない（5.1-⑪）。標準パラメータは無料 |
| AWS Budgets                 | コスト超過通知         | §5 コスト                                                                   |
| Terraform                   | IaC             | §6 制約条件                                                                  |




### S3 ストレージクラスの割り当て

コスト要件（400GBを月額1,000円以内）を満たすため、**ライフサイクル制御が必須**となる。全てStandardに置くと月額約1,500円で超過する。


| 対象            | クラス                       | 変更タイミング                         |
| ------------- | ------------------------- | ------------------------------- |
| 最新版PDF        | Standard                  | アップロード時の既定                      |
| 最新版Excel      | Standard-IA               | アップロード時。署名条件に `x-amz-storage-class` を含める |
| 旧版（PDF・Excel） | Glacier Instant Retrieval | 「旧版」遷移時に非同期Lambdaが `CopyObject` |


同一キーへの `CopyObject` でクラスのみ変更するため、台帳のS3キー属性は書き換え不要。

#### 単価と計算根拠

単価は AWS Pricing API から取得した東京リージョンの値（公表日 2026-08-07）。


| クラス                        | 単価（$/GB・月） |
| -------------------------- | ---------- |
| S3 Standard                | 0.0250     |
| S3 Standard-IA             | 0.0138     |
| S3 Glacier Instant Retrieval | 0.0050     |


想定容量400GB（PDF 100GB / Excel 300GB・いずれも旧版を含む）で、平均リビジョン数を3
（＝全体の1/3が最新版）とした場合の月額。

```
全てStandard : 400GB × $0.025                                   = $10.00
使い分け      : 最新PDF  33GB × $0.0250 = $0.83
               最新Excel 100GB × $0.0138 = $1.38
               旧版     267GB × $0.0050 = $1.33                 = $3.55
```

**$10.00 は ¥150/USD で約¥1,500、¥160/USD で約¥1,600**となり、いずれもコスト要件（月1,000円）を超える。
使い分ければ $3.55（¥568〜¥630）に収まる。**削減率は平均リビジョン数によって57〜71%。**

想定容量400GBは**今後10年でも前提が崩れないよう余裕を見た数字**である。現在の実ファイルサイズ
（PFMEA・QC工程表は1MB未満、作業指示書はExcelで10〜50MB・PDFはその数分の一）から試算すると
実データは数十GB規模で、その範囲では全てStandardでも要件内に収まる。
**それでも使い分けを実装するのは、想定容量に近づいた時点で必須になるため。**

#### ストレージ以外の内訳

利用前提を「閲覧450件/月（平均5MB）・ダウンロード50件/月（平均20MB）・発行改訂5件/月」とした場合。


| 項目                    | 月額（$）  | 備考                        |
| --------------------- | ------ | ------------------------- |
| データ転送（S3→インターネット）     | 0.3618 | 月3.17GB × $0.114/GB       |
| Standard-IA 取り出し      | 0.0098 | $0.010/GB                 |
| DynamoDB（オンデマンド）      | 0.0085 | 一覧取得の Scan が主             |
| API Gateway           | 0.0059 | REST API $3.50/100万リクエスト  |
| CloudFront リクエスト      | 0.0022 | $0.012/10,000 HTTPSリクエスト  |
| S3 リクエスト              | 0.0002 | PUT $0.0000047 / GET $0.0000004 |
| Lambda                | 0      | 無料枠内（月100万リクエスト・40万GB秒）   |
| **小計**                | **0.39** | **全体の1割未満**             |


**ストレージとデータ転送以外は無視できる規模。** 要件を左右するのはストレージである。

**ファイルはCloudFrontを経由しない**（署名付きURLでS3から直接取得する）。CloudFrontが配信するのは
画面のアセットのみで、合計約50KB。なお**CloudFrontのキャッシュはデータ転送料を減らさない** —
キャッシュが減らすのはオリジンへの取得回数で、S3からCloudFrontへの転送は元々無料のため。

#### 為替レートの扱い

コスト要件は円建て、AWS Budgets の予算はドル建て（6 USD）で設定している。
**¥167/USD を超えると 6 USD が¥1,000を上回り、予算アラートが要件超過を検知できなくなる。**
円安が進んだ場合は予算額を見直すこと。

## ディレクトリ構成

```
q-documents/
├── docs/           # 設計ドキュメント
├── infra/          # Terraform
├── shared/         # 型定義（backend / frontend の両方から参照）
├── backend/        # Lambda（Node.js 22 + TypeScript）
│   └── src/
│       ├── handlers/   # 同期API・非同期
│       └── lib/        # 文書番号パース・状態遷移などの純粋関数
├── frontend/       # Vite + vanilla TypeScript
└── CLAUDE.md       # このアプリ固有の設計判断
```

`shared/` **に型定義を置き、両側から相対パスで読む。** モノレポ用のツールは導入しない（学習対象を増やさないため）。

```typescript
// shared/types.ts
export type DocumentStatus =
  | 'ファイル未登録' | '一部登録' | '最新' | '旧版' | '削除済み';

export type DocumentRecord = {
  productCode: string;   // PK: 製品コード
  sortKey: string;       // SK: 文書ID#リビジョン
  documentNo: string;
  documentType: string;
  processNo?: string;
  processName?: string;
  revision: string;      // 2桁ゼロ埋め
  owner: string;
  issuedAt: string;
  registeredAt: string;
  status: DocumentStatus;
  s3KeyPdf?: string;
  s3KeyExcel?: string;
};
```

## 採用しなかった技術と理由

一部は要件定義書 §4.3（対象外）と対応する。**代替案を検討した上での判断であることを記録する。**


| 技術                                   | 不採用の理由                                                                 | 再検討の条件                       |
| ------------------------------------ | ---------------------------------------------------------------------- | ---------------------------- |
| React                                | 学習対象が TypeScript + AWS + React の3つになり、いずれも浅くなる。画面7枚の規模では恩恵が学習コストを下回る | 次案件。TypeScriptが手に馴染んだ状態で着手する |
| AWS WAF                              | 月額約900円でコスト要件を超過。IP制限はCloudFront FunctionsとREST APIリソースポリシーで無料実現できる    | 汎用攻撃への多層防御が必要になった場合          |
| API Gateway HTTP API                 | リソースポリシー非対応のため、無料でのIP制限ができない                                           | —                            |
| Amazon RDS                           | 月額コストが要件を超過                                                            | データ規模が拡大し複雑な集計が必要になった場合      |
| SSE-KMS（顧客管理キー）                      | SSE-S3で保管時暗号化の要件を満たせる。キー1本あたり月約150円                                    | キー単位の監査ログとローテーションが必要になった場合   |
| LocalStack                           | CloudFront・リソースポリシー・署名付きURLの再現性が低い                                     | —                            |
| Amazon Cognito                       | 個人単位の認証・ユーザー管理は要件定義書 §4.3 で対象外。役割単位の合言葉（SSM Parameter Store + Lambdaでの検証）で代替する。合言葉は共有されるため本人性は証明できないが、要求される保護水準（生産技術以外を入れない）には足りる | 個人単位の監査が必要になった場合。実運用導入時の課題としてREADMEに記載する |
| Playwright（E2E）                      | 開発期間4週間では優先度が下がる。受け入れ基準25項目の手動確認で代替                                  | 期間に余裕が出た場合                   |
| Tailwind CSS 等のCSSフレームワーク            | 画面数が少なく、記法習得の時間を実装に回すべき                                                | —                            |
| Excel→PDF自動変換（LibreOffice on Lambda） | 変換の忠実性が担保できず、罫線・印刷範囲が厳密な帳票では品質事故につながる。工数も3〜5日必要                        | —                            |

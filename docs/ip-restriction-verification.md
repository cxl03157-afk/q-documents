# IP制限の技術検証

**実施日: 2026/7/31（週1・1日目）／ 判断期限: 8/5**

## 目的

要件定義書 §5.1-③「画面・APIともに社内ネットワーク（グローバルIP）からのアクセスのみ許可する」を、
**AWS WAF を使わずに**実現できるかを実測で確定させる。

WAF は月額約900円かかり、コスト要件（月1,000円以内）を単独で圧迫する。
無料の代替手段が使えることを確認できれば、要件定義書 §4.3「AWS WAFによるマネージドルール適用（不採用）」の
根拠が実測で裏付く。使えなければ、コスト要件そのものの改訂が必要になる。

**Terraform は書かない。** 使い捨てのリソースを手で作り、確認したら壊す。
本番のコード化は週1・6〜7日目に行う。

## 事前準備

```bash
curl -s https://checkip.amazonaws.com
```

表示された値が**自分の現在のグローバルIP**。以下ではこれを `<自IP>` と記す。

許可リスト外のテストには `203.0.113.0/24`（RFC 5737 のドキュメント用アドレス。実在の通信に使われない）を使う。

> **社内グローバルIPは今日は不要。** 2状態テスト（自IP ↔ ドキュメント用アドレス）で両方向を確認できる。
> **public リポジトリなので、IPアドレスをこのファイルに書かないこと。**



### 「社内IP」の扱いについて（重要な前提）

本アプリの題材は開発者が**以前勤めていた会社**の課題であり、**現在その社内ネットワークにはアクセスできない**。
したがって受け入れ基準「社外のIPアドレスからは画面・APIともにアクセスできない」は、
**開発者の自宅回線のグローバルIPを「社内IP」に見立てて**実証する。


| 役割           | 実際に使うもの                      |
| ------------ | ---------------------------- |
| 社内ネットワーク（許可） | 開発者の自宅回線のグローバルIP             |
| 社外ネットワーク（拒否） | **スマートフォンのテザリング**（別のグローバルIP） |


**この方式を選んだ理由**: 受け入れ基準が求めているのは「**社外から入れないこと**」であり、
それを示すには別のグローバルIPが1つあれば足りる。EC2 を社内PCに見立てる案も検討したが、
ブラウザで画面の403を見せるには SSM 経由のプロキシ等が必要になり、
実証できる内容が増えないまま手数だけが増えるため採らない。

**設計上の担保**: 許可IPは Terraform 変数（CIDRのリスト）で外から渡す。
**社内IPに差し替えるだけで本番運用できる**ことは構成で示せる。

**運用上の注意**: 家庭用回線のグローバルIPは変わり得る。
**デモの直前に** `curl -s https://checkip.amazonaws.com` **で自IPを確認する。**
変わっていたら tfvars を更新して apply（数分）。確認を怠ると当日自分も締め出される。

この前提は README（週4作成）の「実運用時の課題」に明記する。

## 手順1: CloudFront Functions（先に作る）

配信完了まで数分かかるため、これを先に作り、待ち時間に手順2を進める。

### 1-1. 関数を作成

CloudFront コンソール → **関数（Functions）** → 関数を作成

- 名前: `q-doc-ip-test`
- ランタイム: **cloudfront-js-2.0**

コードに以下を貼り、「変更を保存」→ **発行（Publish）タブで「関数を発行」**。

```js
function handler(event) {
  var allowed = ['203.0.113.10'];   // まずは許可リスト外の状態から始める
  var ip = event.viewer.ip;
  if (allowed.indexOf(ip) === -1) {
    return {
      statusCode: 403,
      statusDescription: 'Forbidden',
      headers: { 'content-type': { value: 'text/plain' } },
      body: 'blocked: ' + ip        // 検証用にIPを返す（本番では返さない）
    };
  }
  return event.request;
}
```

**発行しないと関連付けできない。** 保存とは別の操作である点に注意。

### 1-2. テスト用ディストリビューションを作成

CloudFront → ディストリビューションを作成


| 項目                   | 値                                      | 理由                                                                     |
| -------------------- | -------------------------------------- | ---------------------------------------------------------------------- |
| オリジンドメイン             | `example.com`                          | **何でもよい。** 関数はオリジンに到達する前に走るため、IP判定の検証にオリジンの正しさは関係しない。S3+OAC を手で組む時間を省く |
| プロトコル                | HTTPS only                             |                                                                        |
| ビューワープロトコルポリシー       | **Redirect HTTP to HTTPS**             | 受け入れ基準「HTTPでアクセスするとHTTPSにリダイレクトまたは拒否される」の下見を兼ねる                        |
| 関数の関連付け → ビューワーリクエスト | CloudFront Functions → `q-doc-ip-test` |                                                                        |
| **セキュリティ保護（WAF）**    | **有効にしない**                             | **ここで有効にすると月約8ドル発生する。** 今回の検証目的そのものに反する                                |


作成後、`dxxxxxxxxxx.cloudfront.net` 形式のドメイン名を控える。**「最終デプロイ日時」が更新されるまで数分待つ。**

### 1-3. 確認（許可リスト外の状態）

```bash
curl -i https://dxxxxxxxxxx.cloudfront.net/
```

- 期待: **403** / 本文 `blocked: <自IP>`
- **本文に出たIPが** `curl https://checkip.amazonaws.com` **と一致するか確認する** → 項目B



### 1-4. 許可リストを自IPに変えて再確認

関数のコードの `allowed` を `['<自IP>']` に変更 → 保存 → **発行** → 数分待つ → 再度 curl

- 期待: 403 **以外**（example.com のレスポンスが返る。404 や 200 のどれでもよい）



### 1-5. HTTPリダイレクトの確認（ついで）

```bash
curl -i http://dxxxxxxxxxx.cloudfront.net/
```

- 期待: **301** で `https://` へのリダイレクト

## 手順2: API Gateway リソースポリシー（CloudFront の待ち時間に実施）



### 2-1. APIを作成

API Gateway コンソール → APIを作成 → **REST API**（プライベートではない方）

- 名前: `q-doc-ip-test`
- **エンドポイントタイプ: リージョン（Regional）** ← 項目E



### 2-2. Mock でGETメソッドを作る

リソース `/` → メソッドを作成 → **GET** → 統合タイプ: **Mock** → 作成

Mock は Lambda を作らずに200を返せるため、IP制限だけを切り分けて確認できる。

### 2-3. リソースポリシーを設定

「リソースポリシー」に以下を貼って保存。

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": "*",
      "Action": "execute-api:Invoke",
      "Resource": "execute-api:/*"
    },
    {
      "Effect": "Deny",
      "Principal": "*",
      "Action": "execute-api:Invoke",
      "Resource": "execute-api:/*",
      "Condition": {
        "NotIpAddress": { "aws:SourceIp": ["203.0.113.0/24"] }
      }
    }
  ]
}
```

**Allow + 条件付きDeny の2文にする理由**: Allow だけを条件付きにすると、条件から外れたリクエストは
「暗黙の拒否」で落ちる。明示的な Deny にしておくと、後から読んだときに意図が残る。

### 2-4. デプロイ（ここが落とし穴）

「APIをデプロイ」→ 新しいステージ `test`

> **リソースポリシーは変更しただけでは効かない。ステージを再デプロイして初めて反映される。**
> 「設定したのに弾かれない」の原因はほぼこれ。→ 項目D



### 2-5. 確認（許可リスト外の状態）

```bash
curl -i https://xxxxxxxxxx.execute-api.ap-northeast-1.amazonaws.com/test/
```

- 期待: **403** / 本文に `User: anonymous is not authorized to perform: execute-api:Invoke`



### 2-6. 許可リストを自IPに変えて再確認

リソースポリシーの `203.0.113.0/24` を `<自IP>/32` に変更 → 保存 → **必ず再デプロイ** → curl

- 期待: **200**

## 結果



### 最大の発見: CloudFront は既定で IPv6 有効。`viewer.ip` に IPv6 が入る

許可リスト外の状態でアクセスしたところ、403 は返ったが本文のIPが **IPv6アドレス**だった。
同時刻に `curl https://checkip.amazonaws.com` が返す自IPは **IPv4** であり、両者は一致しない。

**このまま本番へ出すと、社内のIPv4グローバルIPだけを許可リストに入れても、
IPv6で接続できる環境の利用者が全員403になる。**
「一部の人だけ画面が開けない」という形で出るため、原因特定に時間がかかる種類の障害。

ディストリビューションの **IPv6 を無効化**（`IsIPV6Enabled = false`）して再テストしたところ、
`viewer.ip` は期待通り **IPv4** になった。

→ **本番の Terraform では** `is_ipv6_enabled = false` **を必ず指定する。**

代替案として社内のIPv6プレフィックスを許可リストに追加する方法もあるが、
プレフィックスの把握と変動リスクが増えるため採らない。

| D   | **判明**       | 3つとも「保存しただけでは効かない」型。①CloudFront Functions は保存（DEVELOPMENT）→**発行**（LIVE）②ディストリビューション設定変更は**再配信1〜3分** ③API Gateway リソースポリシーは保存→**ステージ再デプロイ**→さらに**反映まで約90秒**（再デプロイ直後は403のまま。焦って設定を触ると原因を見失う） |

### 403 の出どころの見分け方

応答ヘッダー `x-cache: FunctionGeneratedResponse from cloudfront` が付いていれば、
CloudFront Functions が生成した403である（WAFやオリジンによる403ではない）。
本文に `blocked: <IP>` を入れておいたことと合わせて、切り分けができた。

### 明示的な Deny にした効果

拒否時のレスポンスに `with an explicit deny in a resource-based policy` と理由が出た。
Allow の Condition だけで書いた場合（暗黙の拒否）ではこの一文は出ず、
「なぜ弾かれたのか」を切り分ける材料が減る。2文構成にした判断は妥当だった。

### リージョンの取り違え（作業上の注意）

API Gateway を **us-east-1** に作ってしまい、`ap-northeast-1` のURLを叩いて空応答になった。
CloudFront の画面はリージョンを持たない（グローバル）ため、そこから API Gateway に移ると
**リージョンが切り替わっていることに気づきにくい。**

本番は Terraform でプロバイダのリージョンを明示するため、この取り違えは構造的に起きない。
（ただし CloudFront 周辺には us-east-1 必須のリソースがあるため、その扱いは週1・6〜7日目に整理する。）

### 副次的に確認できたこと

HTTP でアクセスすると **301 で HTTPS にリダイレクト**された（ビューワープロトコルポリシー `Redirect HTTP to HTTPS`）。
要件定義書 §7 の受け入れ基準「HTTPでアクセスするとHTTPSにリダイレクトまたは拒否される」の下見が済んだ。

### 要確認事項（8/5の判断前に調べる）

CloudFront の新しいコンソールでは、ディストリビューション作成時に
**「Security protections from WAF are included in your plan at no additional charge」** と表示され、
基本的なWAF保護（一般的な脆弱性対策・脅威インテリジェンスによるIPブロック・レート制限）が
プランに含まれると読める（今回作成したものは `Free plan` / `$0/月` 表示）。

要件定義書 §4.3 の「WAFは月額約900円のため不採用」という前提が古い可能性がある。
ただし今回必要なのは**社内IPのみを許可する許可リスト型のカスタムIPルール**であり、
表示されている無料分（悪性IPのブロック＝拒否リスト型）とは用途が異なる。
**カスタムIPルールが無料枠に含まれるかは未確認。**

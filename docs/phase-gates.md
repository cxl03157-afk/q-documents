# ゲートチェックリスト

作業の区切り（1日の開始・実装の前・1日の終わり・セッションの切り替え）で毎回使う。
「開始前」「実装前」「実行中」「終了時」「引き継ぎ」を同じ形式で確認する。

工程の単位は `docs/phase-roadmap.md` の**週・日**とする。

---

## 1. 開始前チェック（Start Gate）

- [ ] `docs/context.md` を読み、現在の週・日と NextAction を把握した
- [ ] `docs/phase-roadmap.md` で当日の作業内容を確認した
- [ ] 必要に応じて設計ドキュメント（`要件定義書.md` / `screens.md` / `API.md` / `DynamoDBテーブル設計.md` / `tech-stack.md`）を参照した
- [ ] `CLAUDE.md` の該当ルール（採番・状態遷移・責務分担・ブランチ命名など）を確認した
- [ ] その日の作業計画（実装順序・リスク・成果物）を立案し、ユーザーに提示した
- [ ] 計画をユーザーが承認した
- [ ] GitHub Issue を作成した（**機能のまとまり単位**。目的・完了条件を記載。PR 1本ごとには立てない）
- [ ] main から作業ブランチを作成した（`feature|fix|docs|refactor/issue-{番号}-{内容}`）

---

## 2. 実装前チェック（Implementation Gate）★このプロジェクト固有

**CLAUDE.md §1 の実装ゲート。コードを書き始める前に必ず通す。**

- [ ] **何をどう書くかを日本語で説明した**（ファイル構成・関数の責務・データの流れ・エラー時の挙動）
- [ ] 説明に対してユーザーの承認を得た
- [ ] 複数の副作用にまたがる処理（DynamoDB + S3、同期API + 非同期Lambda）の場合、**異常系の設計**を説明に含めた
- [ ] 既存の設計ドキュメントと矛盾しないことを確認した（矛盾する場合は §3 の仕様変更ゲートへ）

**説明が未提示の場合、実装に進まない。**

---

## 3. 実行中チェック（In-Phase Gate）

- [ ] スコープ外の作業を実施していない
- [ ] 重要な設計判断を `docs/context.md` の「直近の決定事項」に追記した
- [ ] 新しい未解決事項を `docs/context.md` の「未解決」に追記した
- [ ] **仕様変更ゲート** — APIパス・リクエスト/レスポンス・DBスキーマ・認証認可・エラー仕様を承認済み計画から変更する場合、作業を止めて変更理由・影響範囲・更新対象ドキュメントを提示し、承認を得た
- [ ] 次のセッションが再開できる情報が `docs/context.md` に残っている

---

## 4. 終了時チェック（End Gate）

- [ ] その日の完了条件を満たしている（Issue の完了条件）
- [ ] `npm run lint` → `npm test` → **`npm run build`** をこの順で通した（**lint と test だけで CI グリーン相当と判断しない**）
- [ ] テスト結果を提示した。**失敗・未実施の項目は「未実施」と明記した**
- [ ] そのPRで動くようになったものを実際に触って確認した
- [ ] **該当する受け入れ基準（要件定義書 §7・全25項目）を確認し、消化数を `docs/context.md` に記録した**
- [ ] `docs/context.md` の 週/日 / ブランチ / NextAction を更新した
- [ ] PR本文に `Closes #<issue>` が入っている
- [ ] **CLAUDE.md の「push 前チェックリスト」を実施し、承認を得てから push した**
- [ ] **1日1回の push を完了した**（PRが未完成でもよい。目的はバックアップ）

---

## 5. 引き継ぎチェック（Handoff Gate）

- [ ] `docs/context.md` が最新である（次のセッションはこれ1枚から始まる）
- [ ] 次に読むべきファイルを明記した（`CLAUDE.md` / `docs/context.md` / 対象Issue）
- [ ] 対象Issue番号（`#<issue>`）を明示した
- [ ] **「次の1アクション」が1つだけ定義されている**
- [ ] セルフレビューで確認すべき論点（仕様・セキュリティ・テスト）を残した

---

## 6. インフラ作業時の追加チェック

コードのPRとは順序が逆になる（`CLAUDE.md` §11）。

- [ ] ブランチ上で `terraform plan` の内容を確認した
- [ ] ブランチ上で `terraform apply` が成功した
- [ ] **apply 成功を確認してからマージした**
- [ ] 社内グローバルIPなどの秘匿値がコミット対象に含まれていない（`git status` で確認）
- [ ] 作成したリソースが想定通りか、AWSコンソールまたはCLIで確認した

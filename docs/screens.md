# 画面設計

## 1. 画面一覧

ルーティングは**ハッシュ方式**（`#/documents/new` 形式）とする。S3 + CloudFront の静的配信でサーバー側の書き換えが不要になり、SPAルーティング用の CloudFront Function を追加せずに済むため。


| ID  | 画面         | パス                           | 合言葉   | 対応機能                   |
| --- | ---------- | ---------------------------- | ----- | ---------------------- |
| S-1 | 一覧・検索      | `#/`                         | 不要    | F-05, F-06, F-08, F-11 |
| S-2 | 生産技術モード解除  | `#/unlock`                   | —     | F-18                   |
| S-3 | 新規文書発行     | `#/documents/new`            | **要** | F-02, F-07, F-10       |
| S-4 | リビジョンアップ   | `#/documents/{docNo}/revise` | **要** | F-03, F-07             |
| S-5 | ファイルアップロード | `#/documents/{docNo}/upload` | **要** | F-01, F-09             |
| S-6 | マスタ管理      | `#/masters`                  | **要** | F-10                   |
| S-7 | 台帳の修正・論理削除 | `#/documents/{docNo}/edit`   | **要** | F-13                   |


F-06（関連文書の表示）は画面を増やさず、S-1 内のパネルで表示する。

        ┌────────────────────────────────────────────────┐
        │   S-1（解除済み・書き込み導線が出現）             │
        └───┬──────────┬──────────┬──────────┬────────────┘
            │          │          │          │
            ▼          ▼          ▼          ▼

**ロック状態では S-3〜S-7 への導線を表示しない。** URLを直接叩いた場合も S-2 へリダイレクトする。

## 3. 共通ヘッダー

全画面に表示する。**現在どちらの状態にいるかを常に見えるようにする**（解除し忘れ・解除したまま離席の両方を防ぐため）。

**ロック時**

```
┌────────────────────────────────────────────────────────┐
│ Q-documents                        生産技術の方はこちら → │
└────────────────────────────────────────────────────────┘
```

タイトル `Q-documents` は S-1（`#/`）へのリンクにする。

書き込み導線は非表示だが、**解除画面への入口だけは常設する**。これがないと生産技術の担当者が S-2 に到達できない。

**解除時**

```
┌──────────────────────────────────────────────────────────────┐
│ Q-documents  [一覧] [新規発行] [マスタ管理]  山田太郎（生産技術） [終了] │
└──────────────────────────────────────────────────────────────┘
```

**`[一覧]` をタイトルと別に置く。** タイトルもリンクにしてあるが、「ロゴを押すとホームに戻る」
という慣習は PC操作に不慣れな利用者には通じない前提で作る（§6）。
これがないと **S-3・S-6 から一覧に戻る手段が `[終了]`（＝解除の終了）しかなくなる**。

## 4. ロック状態の管理


| 項目         | 仕様                                                      |
| ---------- | ------------------------------------------------------- |
| トークンの保持先   | `sessionStorage`（タブを閉じると消える）                            |
| 明示的な解除終了   | ヘッダーの「終了」ボタン。トークンを破棄し再描画                                |
| 自動ロック      | **30分間の無操作**でロック状態へ戻す                                   |
| 自動ロックの予告   | 入力中のフォームがある場合、残り1分で警告を表示                                |
| サーバー側の有効期限 | 8時間（業務時間相当）。クライアントが壊れていても Lambda 側で拒否する                 |
| トークン失効時の挙動 | API が 401 を返したら自動的にロック状態へ戻し「セッションが終了しました。再度解除してください」と表示 |


無操作タイマーはクリック・キー入力・スクロールでリセットする。

## 5. 各画面の仕様



### S-1 一覧・検索（`#/`）

**目的** 全利用者が文書を探し、最新版のPDFを開く。生産技術は解除後にエクセル・旧版も扱う。

**絞り込み**（F-05）


| 項目    | 形式       | 備考                                                                   |
| ----- | -------- | -------------------------------------------------------------------- |
| 製品コード | チェックボックス |                                                                      |
| 工程番号  | チェックボックス | 選択肢に工程名を併記する（`K001（工程1）`）。工程名は工程番号と1対1のため、別々の絞り込みにすると食い違った組み合わせを選べてしまう |
| 文書種類  | チェックボックス |                                                                      |
| 状態    | チェックボックス | 既定は「最新」。「一部登録」を選べば登録漏れを抽出できる。**「削除済み」は解除時のみ選択肢に出す**（一般利用者に見せる必要がないため）  |


いずれも複数選択可。絞り込みは画面側で行う（`GET /documents` は全件を返す）。

**プルダウン（`<select multiple>`）ではなくチェックボックスで出す。**
複数選択プルダウンは Ctrl/⌘＋クリックが必要で、普通にクリックすると他の選択が消える。
PC操作に不慣れな利用者が対象のため（§6 全画面に共通する方針）、この画面では使えない。
選択肢の枠は高さを固定し、候補が増えたら枠の中だけスクロールさせる
（フォーム全体が伸びると一覧が下に押し出されるため）。

**検索の選択肢には無効化されたマスタも出す**（末尾に `（無効）` を付け、有効なものの後ろに並べる）。
登録（S-3）が有効なマスタだけを出すのとは扱いを変える。
マスタの無効化は「今後これで新規発行しない」という意味であって、過去の記録を隠すことではない。
検索から外すと、廃番になった瞬間にその製品の文書へ到達できなくなる。

**一覧テーブル**

文書番号 / 文書種類 / 製品コード / 工程番号 / 工程名 / Rev / 状態 / 担当者 / 文書発行日 / 操作

- 状態が「一部登録」の行は警告色で強調する（片方のファイルが未登録の状態が放置されると、旧版が「最新」のまま残るため）

**行の表示とファイルの取得を区別する。** 合言葉が制御するのは**ファイルの取得**であり、一覧に出る行そのものではない。


|                          | ロック時                    | 解除時   |
| ------------------------ | ----------------------- | ----- |
| 最新版の行                    | 表示される                   | 表示される |
| **旧版の行**                 | **表示される**（状態フィルタで選べば出る） | 表示される |
| 最新版の `[PDF]` ボタン         | 表示される                   | 表示される |
| 最新版の `[エクセル]` ボタン        | 表示しない                   | 表示される |
| 旧版の `[PDF]` `[エクセル]` ボタン | 表示しない                   | 表示される |
| **削除済みの行**                | **選択肢に出ないため表示されない**        | 状態で選んだ場合のみ表示される |
| 削除済みの `[エクセル]` ボタン        | 表示しない                   | **表示される**（万一のときに中身を確認するため） |
| 削除済みの `[PDF]` ボタン          | 表示しない                   | **表示しない**（配布物なので、消した版を現場に出さない） |


状態フィルタの既定値は「最新」なので、通常は旧版の行は目に入らない。台帳のメタデータ（文書番号・状態・担当者）は社内利用者に隠す必要がないため、あえて選んだ場合は表示する。

**関連文書パネル**（F-06）

行を選択すると一覧の下部に表示。同一製品コードの最新版を PFMEA / QC工程表 / 作業指示書 に分けて並べる。
**該当がない種類は「なし」と表示する** — 行ごと消すと、未作成なのか表示し忘れなのかが区別できない。
3点セットで揃っているべき文書なので、欠けていることに気づける形にする。
ただし**共通コード（F-10）の場合は製品単位の種類（PFMEA・QC工程表）を行ごと出さない**。
そもそも存在しないため、「なし」が欠品の警告に見えてしまう。

**その他の操作**

- `[CSV出力]` — 表示中の内容（全件・絞り込み結果とも）をダウンロード（F-08）
- `[PDFをまとめてダウンロード（N件）]` — **表示中の行**が対象（F-11）。解除時は `[エクセルをまとめてダウンロード]` も出す。
  対象は行ごとのボタンと同じ条件（ロック時は最新のPDFのみ、解除時は旧版とエクセルも）。
  **押す前に件数をボタンに出し、上限（50件）を超える場合は実行せず「絞り込んでください」と表示する** —
  絞り込みなしで押すと台帳の全件が対象になり、ブラウザ側が破綻するため。
  ZIPでまとめる方式は採らない（Lambdaで大容量を集めて圧縮すると実行時間・メモリ・コストが合わない）。
  実装は `GET /documents/{docNo}/download-url` を件数分呼ぶだけで、新しいAPIは要らない
- 解除時のみ、行に `[リビジョンアップ]` `[修正]` を表示
- 解除時のみ、**状態が「ファイル未登録」の行に `[アップロード]` を表示**する。
  採番した日とファイルが揃う日が別になるため、S-3 の登録直後のボタンだけでは S-5 に戻れない。
  「一部登録」の行には出さない — S-5 は同一種別が登録済みだと拒否するため（F-01）、
  押せるのに必ず失敗する導線になる。詰まったレコードは `[修正]` から論理削除して発行し直す

**API** `GET /documents`、`GET /masters`、`GET /documents/{docNo}/download-url`

### S-2 生産技術モード解除（`#/unlock`）

**目的** 氏名を記録し、合言葉を検証して書き込み・エクセル閲覧を解放する。

**入力**


| 項目  | 形式      | 備考                   |
| --- | ------- | -------------------- |
| 氏名  | プルダウン   | 担当者マスタ（生産技術のみ登録）から取得 |
| 合言葉 | パスワード入力 | 伏字表示                 |


**操作** `[解除]` → `POST /auth/unlock` → トークンを `sessionStorage` に保存 → S-1 へ戻る

**エラー表示** 「氏名または合言葉が違います」とだけ表示する。どちらが誤りかは示さない。

---



### S-3 新規文書発行（`#/documents/new`）

**目的** 命名ルールに従って文書番号を採番し、台帳に登録する。

**入力**（すべてマスタからのプルダウン選択。F-10）


| 項目    | 備考                                                                                            |
| ----- | --------------------------------------------------------------------------------------------- |
| 文書種類  | 選択内容により以下の欄の表示が変わる。**共通コード（F-10）を選んだ場合は工程単位の種類だけを表示する**（共通作業に PFMEA・QC工程表は存在しないため）  |
| 製品コード | プルダウン（候補が増えた場合は入力補完を検討）                                                                       |
| 工程番号  | **採番ルールが「工程単位」の文書種類を選んだ場合のみ表示**（PFMEA・QC工程表は製品単位のため不要）                                        |
| 工程名   | **工程番号の選択に応じて自動表示。単独では選べない**（マスタ上 工程番号と工程名は1対1のため、対で選ばせると `K001`＋`工程2` のような実在しない組み合わせが作れてしまう） |
| 担当者   |                                                                                               |
| 文書発行日 | 日付入力                                                                                          |


**操作の流れ**

1. `[番号を生成]` → `POST /documents/number-preview` → 生成された文書番号を確認画面に大きく表示
2. 「この番号を文書に記入し、ファイル名にも付けてください」と案内
3. `[登録]` → `POST /documents` → 状態は「ファイル未登録」で記録される
4. `[ファイルをアップロードする]` → S-5 へ

マスタに存在しない製品コード等がある場合は、S-6 へ移動して追加してから戻る。

**既に同じ文書が存在する場合は番号を生成しない。** 文書種類・製品コード（工程単位の場合は工程番号も）が一致する文書が台帳にあるとき、`[番号を生成]` は番号を出さず「この文書は既に登録されています（現行 Rev xx）。リビジョンアップを使ってください」と表示し、S-4 への導線を出す。既存文書と同じ文書IDで Rev 01 を作れてしまうと、同一文書に複数の系列ができて台帳が壊れるため。画面側は早く知らせるためのもので、**正はサーバー側で弾く**。

---



### S-4 リビジョンアップ（`#/documents/{docNo}/revise`）

**目的** 現行文書のリビジョンを1つ進め、新しいレコードを作る。

**表示**（F-03 の「確認画面」に相当）

```
文書番号：Q001_P-0001_01
文書種類：PFMEA
製品コード：P-0001

  現行  Rev 01   →   新規  Rev 02
```

**入力**


| 項目    | 形式            | 既定値             |
| ----- | ------------- | --------------- |
| 担当者   | プルダウン（担当者マスタ） | **現行リビジョンの担当者** |
| 文書発行日 | 日付入力          | **今日**          |


**既定値のまま** `[実行]` **を押せる形にする。** 担当者が変わらない通常のケースで操作を増やさないため。
文書発行日の既定を現行の日付にしないのは、リビジョンアップが新しい版を発行する行為だからである。

文書番号を構成する項目（文書種類・製品コード・工程番号・工程名）は S-4 でも変更できない。
変更すれば別の文書になるため、誤りは論理削除して発行し直す（S-7 と同じ扱い）。

**操作** `[実行]` → `POST /documents/{docNo}/revisions` → 新Revのレコードを「ファイル未登録」で作成 → S-5 へ

**旧版はリビジョンアップできない。** 対象の状態が「旧版」の場合は実行させず、「このリビジョンは旧版です。最新のリビジョンからリビジョンアップしてください」と表示する。旧版から Rev を進めると、既に存在する新Revと文書番号が衝突するため。

旧版へのアーカイブは新Revのファイルが揃った時点で自動的に行われる（F-04）。この画面では行わない。

---



### S-5 ファイルアップロード（`#/documents/{docNo}/upload`）

**目的** PDFとエクセルを同時に登録する。

**表示・入力**

- 対象の文書番号を大きく表示
- PDF欄 と エクセル欄 の2つのファイル選択。各欄に `accept` 属性を付け、選択候補を絞る
- **両方を選択するまで送信ボタンは無効**（F-01：同時選択を必須とする）

**ファイルの検証**

PDFを2つ選ぶ、同じファイルを2回選ぶ、別の文書のファイルを混ぜる — こうした誤りは**送信前に止める**。通過させると、エクセルの実体がPDFのまま台帳が「最新」になり、後日開くまで気づけない。


| #   | 検証内容                      | エラー表示                      |
| --- | ------------------------- | -------------------------- |
| 1   | PDF欄のファイル名が `.pdf` で終わる   | 「PDF欄にはPDFファイルを選択してください」   |
| 2   | エクセル欄のファイル名が `.xlsx` で終わる | 「エクセル欄にはエクセルファイルを選択してください」 |
| 3   | 2つのファイル名の文書番号部分が一致する      | 「2つのファイルの文書番号が一致しません」      |
| 4   | 文書番号が対象文書と一致する            | 「ファイル名の文書番号が対象の文書と異なります」   |
| 5   | 文書番号が命名ルールの形式に従う          | 「ファイル名が命名ルールに従っていません」      |


**1〜5は画面側とサーバー側の両方で検証する。** 画面側は誤りを早く知らせるため、サーバー側は画面の制御を回避されても壊れたデータを作らせないため。サーバー側の検証を通らない限り署名付きURLは発行しない。

あわせて、署名付きURL発行時に `Content-Type` を署名条件に含める。エクセル用URLにPDFを送ると **S3側で拒否される**ため、多層の防御になる。

**操作の流れ**

1. `[アップロード]` → `POST /documents/{docNo}/upload-url` → 2本の署名付きURLを取得
2. ブラウザから S3 へ直接 PUT（2本）
3. 「アップロードが完了しました。台帳への反映を確認しています」と表示
4. 数秒後に `GET /documents` を再取得し、状態が「最新」になったことを確認して S-1 へ

**状態が即座に変わらない点に注意。** 台帳の更新は S3 イベントで起動する非同期 Lambda が行うため、PUT 直後は「ファイル未登録」または「一部登録」のままになる。画面はこれを待つ作りにする。

**エラー表示**（F-01）拒否理由をそのまま表示する。


| 理由        | 表示                                   |
| --------- | ------------------------------------ |
| 未登録の文書番号  | 「この文書番号は台帳に登録されていません」                |
| 旧版のリビジョン  | 「このリビジョンは旧版です。最新のリビジョンにアップロードしてください」 |
| 同一種別が登録済み | 「このリビジョンのPDF（またはエクセル）は既に登録されています」    |


---



### S-6 マスタ管理（`#/masters`）

**目的** プルダウンの選択肢を追加・修正する（F-10）。

**構成** 項目種別をタブで切り替える。

`文書種類` / `製品コード` / `工程番号（工程名）` / `担当者`

**表示・操作**

- コード番号・名称・状態（有効／無効）の一覧
- 文書種類のタブでは**採番ルール**（製品単位／工程単位）を、製品コードのタブでは**共通コード**の区分を編集できる
- `[追加]` → `POST /masters`
- 行ごとに `[修正]` → `PATCH /masters/{id}`
- `[無効化]` — 削除ではなく状態を「無効」にする（過去の文書が参照しているため物理削除しない）

**無効にすると新規発行（S-3）の選択肢から消えるが、検索（S-1）の選択肢には `（無効）` 付きで残る。**
無効化は今後の発行を止める操作であって、過去の文書を探せなくする操作ではない。

担当者に登録するのは**生産技術の担当者のみ**とする。

---



### S-7 台帳の修正・論理削除（`#/documents/{docNo}/edit`）

**目的** 誤登録レコードを直す（F-13）。

**編集できる項目** 担当者 / 文書発行日 — この2つのみ。

**編集できない項目** 文書番号 / 製品コード / 文書種類 / 工程番号 / 工程名 / リビジョン / 状態

- **文書番号を構成する項目は変更できない。** 採番ルール上、文書種類（PFMEA・QC工程表）と工程番号・工程名（作業指示書）は文書番号の一部であり、変更すれば文書番号もSKも変わる。誤っている場合は論理削除して作り直す。
- **状態は編集できない。** ファイル未登録 → 一部登録 → 最新 → 旧版 の遷移は非同期Lambdaが管理する。手で変更できると、ファイルが存在しないのに「最新」になり、F-04のアーカイブ判定も狂う。
- 「一部登録」で詰まったレコードは、論理削除して発行し直す。

**操作**

- `[保存]` → `PATCH /documents/{docNo}`
- `[論理削除]` → 確認ダイアログ → `DELETE /documents/{docNo}` → 状態が「削除済み」になり一覧から消える

## 6. 全画面に共通する方針

**PC操作に不慣れな利用者を想定する。** 現場工程リーダー10名が対象に含まれるため、S-1 は説明なしで使える必要がある。文字入力は極力させず、プルダウンで選ばせる（F-10）。

**エラーは理由を日本語で具体的に示す。** 「エラーが発生しました」で終わらせない。特に F-01 の拒否は、なぜ登録できないかが分からないと現場で詰まる。

**ファイルはブラウザから S3 へ直接送受信する。** 署名付きURLを使い、API Gateway を経由させない（大容量ファイルのため）。

**スマホ対応は行わない**（要件定義書 §4.3）。PC のブラウザ幅を前提とする。
